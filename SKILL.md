# Git Flow & Conventional Commits

## Estructura de ramas

| Rama | Propósito |
|---|---|
| `main` | Código estable, probado y listo para producción. Nunca se desarrolla directamente aquí. |
| `qa` | Integración y validación. Todo cambio pasa por aquí antes de llegar a main. |
| `feat/*` | Nuevas funcionalidades. Ej: `feat/auth-firebase`, `feat/dashboard-stats` |
| `fix/*` | Correcciones funcionales o bugs generales. Ej: `fix/login-error` |
| `bug/*` | Errores específicos detectados. Ej: `bug/modal-close`, `bug/session-expired` |
| `refactor/*` | Mejoras internas sin cambiar comportamiento. Ej: `refactor/auth-logic` |
| `docs/*` | Cambios de documentación. Ej: `docs/readme-update` |
| `test/*` | Pruebas o ajustes de testing. Ej: `test/login-flow` |
| `chore/*` | Mantenimiento general. Ej: `chore/dependencies-update` |

---

## Flujo de trabajo obligatorio

```
rama de trabajo → qa → main
```

Este flujo aplica para todos los tipos: feat, fix, bug, refactor, docs, test, chore.

### Pasos

```bash
# 1. Crear rama desde main (o qa según el equipo)
git checkout -b feat/login-form

# 2. Desarrollar y hacer commits en esa rama

# 3. Integrar en qa
git checkout qa
git merge feat/login-form

# 4. Validar: pruebas, QA, revisión funcional

# 5. Pasar a main solo después de validación
git checkout main
git merge qa
```

> **Regla crítica:** Ningún cambio llega directamente a main. Siempre `rama → qa → main`.

## Conventional Commits

### Formato

```
<type>(<scope>): <description>
```

### Tipos y ejemplos

| Tipo | Uso | Ejemplo |
|---|---|---|
| `feat` | Nueva funcionalidad | `feat(auth): add forgot password flow` |
| `fix` | Corrección funcional | `fix(payments): handle failed webhook retries` |
| `bug` | Error específico | `bug(ui): fix modal close issue` |
| `refactor` | Mejora interna sin cambio de comportamiento | `refactor(user): simplify permission checks` |
| `docs` | Documentación | `docs(readme): update setup instructions` |
| `test` | Pruebas | `test(api): add tests for user service` |
| `chore` | Mantenimiento | `chore(deps): bump lodash to 4.17.21` |
| `style` | Formato visual | `style(ui): format button spacing` |
| `perf` | Optimización de rendimiento | `perf(cache): reduce query execution time` |

## Buenas prácticas

- **Nombres descriptivos:** Evitar `update`, `fixes`, `changes`, `temp`. Preferir nombres que comuniquen qué cambia.
- **Commits atómicos:** Pequeños, claros y fáciles de revertir. Un commit = un propósito.
- **Historial entendible:** Cualquier persona debe poder leer el historial y entender qué se hizo, por qué, dónde y cuándo, sin abrir el código.

## Instrucciones de aplicación para Claude

Cuando el usuario pida ayuda con git en un proyecto:

1. Identificar el tipo de tarea (feat, fix, refactor, etc.) y proponer el nombre de rama correspondiente.
2. Redactar commits siempre en formato Conventional Commits. Si el usuario describe cambios en lenguaje natural, traducirlos al formato correcto.
3. Recordar el flujo obligatorio si el usuario intenta hacer merge directo a main sin pasar por qa.
4. Rechazar nombres genéricos de ramas o commits y proponer alternativas descriptivas.
5. Generar comandos git completos y listos para copiar cuando el usuario lo requiera.

## Regla de autoría — OBLIGATORIA

Claude nunca debe incluir referencias a sí mismo, a la IA, o a su participación en el mensaje de commit, a menos que el usuario lo pida explícitamente.

Esto incluye prohibir frases como:
- `generated by AI`
- `co-authored by Claude`
- `created with Claude`
- `AI-assisted`
- o cualquier variante similar

Los commits deben reflejar únicamente el trabajo y la intención del equipo humano. La participación de Claude en la redacción o generación del commit es irrelevante para el historial del repositorio.
